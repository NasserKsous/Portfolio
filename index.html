Tightrope Walking

Tightrope Walking was introduced in Season 12 and was the first major feature that I worked on. Tightrope Walking is a feature that enables the player to jump on a harpoon line and they can traverse along the harpoon line as long as they can stay on. In order to stay on the line, the player will need to balance but if the player can master this minigame then this opens up a multitude of ways they can use this method to traverse on and off their ship. This was a feature that was started by a previous seasonal team but only made it into the prototype stage before it was shelved. Therefore, my responsibility was to take this prototype and use it as a starting point to implement the Tightrope Walking in a more polished way using the updated design.

The priority I had when working on the tightrope was to work closely with the designer to get a good feel for the balancing minigame that the player will need to do to stay on the tightrope. This took a lot of iteration and collaboration with the designer to get this feeling good to play but once that was done, I could focus on implementing the animations which would help to get the feeling of the minigame to be perfect. Working with animations in Unreal Engine was something that was new to me at the time so this took a bit of time to get correct. I worked with a couple of animators to figure out what they were looking for in terms of a setup for them to plug in their animations. I utilised a mixture of blendspaces and anim sequences due to the different ways a player could use the tightrope. The blendspace was used when the player was walking/running on the tightrope and it would blend between the speed of the player and how close the player was to falling off the tightrope. The animation sequences were used when the player was sliding down the tightrope. Once the animations were sorted, I focused on the final major issues which were that there was a large desync between the server and client positions and orientations of the player on the tightrope. This issue meant that there would be times when the player would fall off the tightrope when it didn't look like they were about to fall off and vice versa. The difficulty came from the fact that the balancing needed to feel smooth for the client so it had to be client-predicted but then the server would need to correct it when the client and server orientations and positions varied too much.

Whilst working on the tightrope walking, I learnt how to work with other disciplines and how to solve client/server desync issues without compromising how the balancing felt for the player.

Crouching

Surprisingly, it took till Season 14 for the ability to crouch to be added to the game. This added a lot of challenges for me to get crouching working in a codebase with systems that weren't designed with crouching in mind. Some of the main aspects that were changed whilst crouching were reduced movement, a smaller hitbox and reduced AI perception. On top of these changes, crouching was also used alongside and was necessary to access 2 other features that were released in Season 14: Disguises and Traps.

I used the knowledge I gained when working on Hit Registration to help me implement the smaller hitbox when crouching. The smaller hitbox was only for projectiles and therefore the collisions with the environment had to stay the same. This meant I had to work with the projectile and rewind systems in Sea of Thieves to be able to accurately adjust the hitbox at the precise time when the player crouched. The reduced AI perception when crouching was implemented by changing the engine code for UE4 so that the AI would have a narrower cone of vision and reduced range of hearing and seeing when trying to detect crouched players. Also design wanted the player to return to crouching whenever they mounted an object (like the cannon or wheel) if they were crouching before mounting. This one part of crouching caused many bugs and issues throughout the development and some even made it into the Retail version. Because of this, a large portion of the time I spent working on crouching was putting out fires that occurred as a result of many systems in the game that were not designed to work with crouching in mind. There were also a couple of exploits that were caused by my implementation of crouching which taught me the hard way how to write secure code that hackers can use to gain an advantage.

In short, crouching was a very difficult feature for me to develop but it was one that taught me a lot about how to create fundamental systems from the ground up and what to keep in mind when creating these systems.

Improving the Hit Registration for projectile weapons

Hit Registration (HitReg) is an issue that all games that involve shooting deal with and it's never an easy one to solve/improve. Sea of Thieves has had poor HitReg but it was highlighted more when the Hourglass mode was introduced in Season 9. This mode added a competitive PvP aspect to the game and as a result, elements of the game such as HitReg were highlighted as not being up to the same standard as other competitive games. I worked on improving HitReg alongside a Principal Programmer at Lucid Games and our task was to monitor the current state and try to improve the HitReg as much as possible.

The first task we had was to monitor the current state of the HitReg using verifiable data alongside the existing sentiment from the playerbase. This verifiable data didn't currently exist so we added some telemetry to measure the number/percentage of client/server agreements and disagreements. We added the telemetry in a way to be able to get a baseline of the HitReg in the most common situations in Sea of Thieves. When we were happy with the telemetry we set up, it got pushed into the Retail version of the game which gave us a huge amount of data to look at to identify the worst scenarios and where we should be focusing on to give the biggest improvement to HitReg. Once we got back the data, we were able to highlight the areas we wanted to improve and once we had made changes that were speculative, we could push that to Retail. We made a lot of changes that were hard to verify internally whether they had improved the HitReg so we were able to use the telemetry to confirm if these changes had made an improvement or not. Another job I had was to take the clips of streamers who had periods of noticeably bad HitReg on stream and dig into the telemetry data to find the clip in our data to get an idea of what caused the HitReg to be considerably bad in that clip. These clips were really helpful to look at because if we were able to reduce the number of times the HitReg can get noticeably worse then this would help with the negative sentiment that would come from these streamers.

In summary, a lot of the work I did to help improve the HitReg in Sea of Thieves was creating and analysing the telemetry data alongside supporting the Principal Programmer with some of the fixes.

Skills I learnt whilst working on this feature:

  • Telemetry/Data Analysis
  • Projectile Code
  • Server and Client Relationships in Unreal Engine

Creating Synthetic Data for use as a dataset for a neural network

This project required a dataset of images/videos of a selection of objects in a scene for a neural network on object detection. The dataset needed was not available open source or was not easy to collect naturally so the dataset needed to be produced synthetically. In order to do this, I used Unigine which is an engine used by Airbus Helicopters for the simulation of the helicopters. I had to consider the different possible scenarios in which these objects may appear in the real world. My part of this project was to provide a way for the user to add/remove/modify weather conditions to the scene in real time.

I created 2 classes for this: a UserInterface class and a Weather class. The user interface class set up the GUI for the user to add/remove/modify weather nodes. To add weather nodes to the scene, an add weather button is present and once clicked will open a file dialog in which the user can select a node to be added to the scene. Once a node is choosen, the node parameters window is shown to modify the parameters of the weather node for use to show different weather conditions. The node parameters window is created using an external xml to define the text boxes and buttons to produce a custom GUI. I created a combo box for the user to selected any of the nodes present in the scene to be modified or deleted. If a node is selected and the edit button is clicked then the node parameters window is shown and once confirmed, the parameters of the selected node are updated. If a node is selected and the delete button is clicked then the node is remove from the scene and removed from the combo box. The Weather class handled the adding, removing and editting of weather nodes. The weather nodes used the node parameters window of the UserInterface class to set and modify parameters such as position, scale, spawn rate and number of particles per spawn.

AI Systems and Enemies for a Hotline Miami style game.

As part of a group project for University, we made a stealthy Hotline Miami style game. For this game, I worked on the AI systems and enemies. A link to the Github page for this game can be found here:
Navigation and Pathfinding.

The AI uses the A* algorithm with waypoints to navigate through the level and this is handled in the Pathfinding class. Firstly, all the walkable tiles are taken in a waypoints and converted into waypoint nodes. When the SetPath function is called, the start and end waypoint node is passed in and a vector of nodes is produced with the necessary waypoint nodes to traverse for the path.

Perception

The AI perception is done using a CanSee and CanHear function. The CanSee function checks to see if the player position is within the vision range and return true if that is the case. The CanHear funciton is a lambda function that is called whenever the SoundPlayed event occurs. It gets all the emitters in range that are playing and return the position of the closest one. The AI will then investigate this position.

Decision Making using a Finite State Machine

The AI uses a Finite State Machine detailed in the State Class. The FSM is implemented using a base state class and the different states are inheritted. The different states are:

  • PatrolState.
  • ChaseState.
  • AttackState.
  • InvestigateState.
  • SearchState.

These are setup so that the state machine can be built for any enemy but can also call the specific functions for each state. Each state has a enter, update and exit function. The enter and exit functions are called once on first switching to the state and upon switching out of the state. These functions are used for switching sprite to the relevant look for the state and to setting a path before traversing this path in the patrol state. This is the AI State Machine Diagram.

Enemies

All the enemies inherit from the CAIController class which acts as the base class for the AI behaviour. This class handles the movement of the enemies and the view semi circle. It also handles the interaction with the pathfinding class the holds virtual functions to be overriden in the inheritted classes. There are 3 types of enemies that inherited from CAIController:

  • AlarmEnemy.
  • DogEnemy.
  • GruntEnemy.
AlarmEnemy

The AlarmEnemy is an enemy that will alert nearby enemies by playing the bell it is holding to make a sound if it sees the player. The nearby enemies will then head to the location of the bell sound. This enemy does not attack the player and is meant to punish the player if they are caught by it.

DogEnemy

The DogEnemy will attack the player using a dash. This works by using 2 timers, one for the attack and one for the cooldown. The dash is emulated by increasing the speed of the dog for a small period of time and the dog will dash in a straight line towards the player. The indication of when the dog is about to attack is done by slowing the dog drastically for a brief period of time before dashing.

GruntEnemy

The GruntEnemy holds a weapon and it will use the weapon if it gets within the weapon's range of the player. This works for both melee and ranged weapons.
